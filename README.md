# DocFlow — комплектование проектной документации

Программа для помощников ГИП: отслеживает изменения в папках проекта,
переименовывает файлы по эталонному реестру наименований, переносит
устаревшие версии в `!ARCHIVE` и формирует комплект актуальной документации
в `8300_ВыпускПД/!LATEST`.

Программа работает **только с локальными и сетевыми папками**, ничего
не отправляет в интернет и не копирует на сторонние серверы. Установка
**не требует прав администратора**.

## Что делает программа

- **Сканирование** выбранных папок-источников и сравнение с предыдущим
  снимком — показывает, что добавилось / изменилось / переместилось.
- **Распознавание** файлов по реестру `…_Наименование файлов.xlsx`: по шифру
  документа (523-ПИР-24-ИОС1.1 и т.п.) определяется эталонное имя файла.
- **Предложение действий** в строгом порядке наведения порядка (ничего не
  выполняется без подтверждения):
  1. *Создать базовую структуру* — в разделе нет папки `!ARCHIVE`: создать её.
     Базовая структура раздела: `!ARCHIVE` + каталог(и) версии `{обозначение}_{дата}`.
  2. *Сформировать каталог и перенести* — посторонний файл лежит прямо в папке
     раздела: создать каталог `{обозначение}_{дата}` и переложить файл в него.
  3. *Каталог-дубль → в архив* — есть две папки-версии одного тома: старую
     целиком в `!ARCHIVE`.
  4. *Переименовать в каталоге* — файл внутри каталога назван не по эталону.
  5. *Переместить в нужную папку* — файл лежит не в той подпапке (pdf не в
     `!PUBLISHED` и т.п.).
  6. *Старый файл → в архив* — устаревший одиночный файл.
  - *Требует внимания* — файл не распознан, неоднозначен или это составной файл.

  Перенос новых версий **с папки субподрядчика на сервер** — отдельная кнопка
  **«Перенести на сервер»** (диалог сверки по дате/CRC32), а не действие плана
  сканирования.

  И только после наведения порядка — кнопка **Сформировать !LATEST**.

### Цветовые индикаторы (статус раздела)

Возле каждого раздела стоит кружок и словесный вердикт:

- 🟢 **в порядке** — есть `!ARCHIVE`, все тома разложены по каталогам и названы
  по эталону, замечаний нет;
- 🟠 / 🔴 **СТРУКТУРА НАРУШЕНА** — нужно навести порядок (нет `!ARCHIVE`, файлы
  вне каталогов, дубли версий, неверные имена и т.п.);
- 🟡 **требует внимания** — структура цела, но есть нераспознанные файлы.

Раздел становится зелёным только когда он действительно полностью в порядке.
Флажок «Только действия» скрывает строки «требует внимания».

### Две папки: сервер и субподрядчик

Добавьте папку субподрядчика как источник (категория ПД). Серверная `4300_ПД`
сканируется автоматически. Чтобы скопировать новую версию с субподряда на
сервер, откройте **«Перенести на сервер»**: программа сравнит даты (и при
совпадении даты — CRC32) и предложит копирование целиком папки версии.
Если такая версия на сервере уже есть — перенос пропускается (без слияния).
Устаревшие каталоги на сервере уходят в `!ARCHIVE` при обычном сканировании.
Файлы у субподрядчика только копируются (не удаляются).
«Серверной» считается папка, совпадающая с «Корнем проекта» + `4300_ПД`;
всё остальное считается внешними источниками.

### Структура тома в 4300_ПД

Для каждого тома/отчёта создаётся папка `{обозначение}_{ггммдд}`, например
`523-ПИР-24-ПЗУ1_260622`, с вложенными папками:

- `!EDIT` — редактируемые форматы (docx, dwg, xlsx и т.п.);
- `!PUBLISHED` — `pdf` и `sig` (с подписями исполнителей).

Файлы раскладываются по этим папкам автоматически: `pdf`/`sig` → `!PUBLISHED`,
остальные форматы → `!EDIT`. Устаревшие версии переносятся в
`{раздел}\!ARCHIVE\{обозначение}_{дата}\…` с такой же структурой.

**Сметная документация** (раздел 12 / шифр `СМ`) раскладывается без
`!EDIT`/`!PUBLISHED` — только папка с версией: `12_СМ\523-ПИР-24-СМ1_260604\<файлы>`.

> Имя папки берётся из обозначения по реестру (например `523-ПИР-24-ПЗУ1`) и
> даты версии. Какие расширения считать «публикуемыми», коды смет и имена
> служебных папок настраиваются в `config.json`
> (`published_extensions`, `smeta_short_codes`, `edit_dir`, `published_dir`).
- **Применение** отмеченных действий с записью в журнал и **откатом**
  последней операции одной кнопкой. В рабочих томах (`4300_ПД`, `1100_ИИ`)
  файлы не удаляются безвозвратно — устаревшее только переносится в `!ARCHIVE`.
  Исключение: обновление и очистка комплекта `!LATEST` могут удалять старые
  версии/лишние копии **после подтверждения** в диалоге.

Эталон наименований берётся прямо из вашего файла
`523-ПИР-24_СП_Наименование файлов.xlsx` (лист «ПИР»). Меняете реестр —
меняются правила. Программистом для этого быть не нужно.

### Окно программы

Окно разделено на две панели:

- **Слева — структура проекта.** Сверху отдельно `📂 4300_ПД — сервер` и
  `📂 Сторонние папки (субподряд)` (а также `1100_ИИ`). Внутри: разделы →
  документы по составу проекта. У каждого узла кружок статуса
  (🟢 в порядке / 🟠 структура нарушена / 🟡 требует внимания).
- **Справа — действия для выбранного узла** с колонкой «Что будет выполнено»
  (откуда и куда переместится/скопируется файл). Отмечаете галочками и
  нажимаете «Применить в этом узле» (или «Применить всё отмеченное»).

Так серверная папка и сторонние папки субподрядчиков не смешиваются:
сразу видно замечания по структуре; перенос новой версии на сервер —
отдельной кнопкой «Перенести на сервер».

## Как собрать DocFlow.exe (один раз)

Нужен установленный **Python 3.10+** (с сайта python.org; при установке
поставьте галочку *Add Python to PATH*). Прав администратора не требуется.

1. Скопируйте папку `_ПрограммаКомплектование` на компьютер.
2. Двойным щелчком запустите **`build_exe.bat`**.
3. Дождитесь сообщения «ГОТОВО». Файл появится в `dist\DocFlow.exe`.
4. Папку `dist` (вместе с `config.example.json`) скопируйте помощникам.

> Если собранный `.exe` блокирует антивирус/политика — можно работать без
> сборки: запускать **`run.bat`** (тоже без прав администратора).

## Первый запуск

1. Запустите `DocFlow.exe`.
2. Нажмите **⚙ Настройки** и укажите:
   - **Корень проекта** — папка проекта на сервере;
   - **Файл реестра** — путь к `…_Наименование файлов.xlsx`;
   - **Папки-источники** — например `4300_ПД` (категория ПД) и `1100_ИИ` (ИИ);
     можно добавить папки субподрядчиков на внешнем диске.
3. Сохраните. Настройки запоминаются в `config.json` рядом с программой.

Готовый шаблон настроек — в `config.example.json` (переименуйте в
`config.json` и поправьте пути, либо настройте через окно).

## Порядок работы

### Шаг 1. Состав проекта (один раз / при изменении состава)

Откройте **⚙ Настройки → раздел «Состав проекта»**:

1. **📋 Сформировать состав из Excel** — программа читает
   `…Наименование файлов.xlsx` и формирует **состав проекта**
   (разделы → документы) в файл `project_structure.json` рядом с программой.
2. При необходимости откройте `project_structure.json` и поправьте состав
   (добавьте/уберите документы, измените шаблоны имён). Excel больше не нужен —
   программа работает с этим JSON.
3. **📁 Создать папки** — программа создаёт по составу структуру на сервере:
   `4300_ПД/01_ПЗ/523-ПИР-24-ПЗ/!ARCHIVE`,
   `4300_ПД/02_ПЗУ/523-ПИР-24-ПЗУ1/!ARCHIVE` и т.д.

### Шаг 2. Наведение порядка (регулярно)

1. **🔍 Сканировать** — слева появится структура проекта со статусами
   (🟢/🟠/🟡), справа — действия для выбранного узла с пояснением
   «Что будет выполнено». Маркер ● — изменилось с прошлого раза.
2. Отметьте действия галочками (столбец ✓). Двойной щелчок — открыть папку.
3. **✔ Применить в этом узле** или **✔✔ Применить всё отмеченное**.
4. **📦 Сформировать !LATEST** — собрать актуальный комплект для заказчика.
5. Ошиблись — **↩ Откатить последнее** вернёт файлы как было.

## Файлы рядом с программой

| Файл | Назначение |
|------|------------|
| `config.json` | настройки (пути, источники, правила) |
| `project_structure.json` | состав проекта (разделы/документы), редактируемый |
| `state.json` | снимок папок для отслеживания изменений |
| `journal.jsonl` | журнал операций для отката |

## Состав проекта (для разработчика)

```
app.py              — окно программы (tkinter)
docflow/
  config.py         — настройки
  registry.py       — чтение реестра наименований из xlsx
  naming.py         — распознавание и формирование имён
  scanner.py        — инвентаризация и отслеживание изменений
  planner.py        — формирование плана действий
  executor.py       — выполнение, журнал, откат
build_exe.bat       — сборка portable .exe (PyInstaller)
run.bat             — запуск без сборки
requirements.txt    — зависимости (openpyxl)
```

Логика наименования настраивается реестром и параметрами в `config.json`;
строгое сопоставление гарантирует, что переименовываются только итоговые
разделы, а рабочие/составные файлы (чертежи, подгрузки) не затрагиваются.
